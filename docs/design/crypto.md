# fib.crypto: an interface for cryptography, and drivers that bind real libraries

Status: the protocol, the encodings and the contracts are built and tested in this repository (`lib/fib/crypto*`, `specs/crypto-*`), including AEAD, key agreement and
signature verification (section 9, CRYPTO-2, 2026-10-07); driver 1 (OpenSSL 3) is built and tested in its own repository, `tailoredshapes/fib-crypto-openssl` (v0.2.0 has them all);
driver 2 (Apple CommonCrypto) is in section 11.
Date: 2026-10-06, extended 2026-10-07. "Measured" means a command was run and its output is quoted in section 10.

## 0. The short answer

1. **Never implement your own cryptography** (the owner's rule, from their cryptography professor). fibber carries **no** hash, MAC, KDF,
   cipher or random generator. It carries an *interface*, a *contract* every implementation must pass, and the part of the job that is
   not cryptography: hex and base64.
2. The interface is a **protocol, `CryptoProvider`**, and the provider is a **value** the program passes to whatever needs it (the
   project's decision for providers, loggers and data sources: no global state, no registry, no implicit default). A driver is a library in its
   own repository with an `(open-provider)` constructor that returns `(Result P CryptoError)`.
3. Every operation returns a `Result`. An algorithm a provider lacks is an `unsupported` error value, never a silent fallback; a provider says
   what it has through a capability list, and the contract checks that the list is honest.
4. Constant-time comparison is **delegated** (`CRYPTO_memcmp`, `timingsafe_bcmp`); fibber has no comparison loop of its own to get wrong.
5. SCRAM-SHA-256 is **protocol logic**: it belongs to the PostgreSQL driver and is built from a provider's HMAC, PBKDF2, digest and random.
   The OpenSSL driver's specs run the RFC 7677 exchange through the provider interface to show the interface is sufficient (section 8).

## 2. The protocols

```clojure
(defstruct CryptoError (kind: str message: str))   ; kind: "unsupported" "invalid-argument" "failed" "closed"

(defprotocol Hasher                                ; a running digest or HMAC: a handle on state the driver owns
  (hasher-update (self data: (Array i8) off: i64 len: i64) -> (Result unit CryptoError))   ; a range: a big input is never copied
  (hasher-finish (self) -> (Result (Array i8) CryptoError))                                ; once; releases the state
  (hasher-close  (self) -> unit))                                                          ; idempotent

(defprotocol CryptoProvider
  (provider-name (self) -> str)
  (provider-capabilities (self) -> (Vec keyword))
  (provider-digest-start (self alg: keyword) -> (Result (dyn Hasher :send) CryptoError))
  (provider-hmac-start   (self alg: keyword key: (Array i8)) -> (Result (dyn Hasher :send) CryptoError))
  (provider-derive (self kdf: Kdf) -> (Result (Array i8) CryptoError))
  (provider-random (self n: i64) -> (Result (Array i8) CryptoError))
  (provider-ct-equal (self a: (Array i8) b: (Array i8)) -> bool))
```

- **Digests.** `:sha-256 :sha-384 :sha-512` are required of every driver. `:sha-1` and `:md5` are *legacy, not for security*: a driver may
  offer them, nothing in fibber needs them for a security decision, and they are named so that using one is deliberate (PostgreSQL's old md5
  authentication, git object ids, HTTP digest compatibility). `(digest p alg bytes)` is one-shot; `(digest-start p alg)`, `(feed h bytes)`,
  `(feed-range h bytes off len)` and `(hasher-finish h)` stream.
- **HMAC** is over any digest the provider has: `(hmac p :sha-512 key data)`, and `hmac-start` streams.
- **Key derivation.** `Kdf` is a value: `(KdfPbkdf2 alg password salt iterations length)`, `(KdfHkdf alg ikm salt info length)`, `(KdfScrypt
  password salt n r p length)`, `(KdfArgon2id password salt iterations memory-kib lanes length)`; `provider-derive` runs one. PBKDF2-HMAC and
  HKDF are required; scrypt and Argon2id are optional and **asked by a capability query**: `(supports? p :argon2id)`, or just call
  `(argon2id p ..)` and get `unsupported` back. A `Kdf` value rather than one method per function keeps the protocol small and lets a driver add
  a function (balloon, bcrypt-pbkdf) by adding a variant in a later version without breaking an implementation that has a `_` arm.
- **Random.** `(random-bytes p n)`: n between 0 and 64 MiB, from the operating system's generator through the library (`RAND_bytes`,
  `arc4random_buf`, `CCRandomGenerateBytes`).
- **Constant-time comparison.** `(ct= p a b)`: false for different lengths (the length is not secret), otherwise the library's constant-time
  compare. `=` on bytes is not for secrets.
- **Capabilities** are keywords: the digests, `:hmac :pbkdf2 :hkdf :scrypt :argon2id :random :ct-equal`. The required set is
  `required-capabilities` in `fib.crypto.contract`.
- **Errors.** `unsupported` (not in the capability list: not a failure of the program, a fact about the build), `invalid-argument` (a count or
  length with no answer: iterations below 1, an HKDF length above 255 times the digest size), `failed` (the library reported an error; the text
  has its message), `closed` (a hasher used after it was finished or closed).

## 3. No global state: how a library takes a provider

The provider is a value. A library that needs cryptography takes **one parameter**, either generic or boxed:

```clojure
(defun scram-start (p: p user: str) :where ((c/CryptoProvider p)) -> ..)       ; generic: a monomorphised copy per driver
(defstruct PgConfig (crypto: (dyn c/CryptoProvider :send) ..))                   ; boxed: stored in a struct, chosen at start-up
(connect cfg) ;; cfg built with (dyn c/CryptoProvider :send provider)
```

A `dyn` provider is itself a `CryptoProvider` (the same functions apply), so the code that calls `c/digest` cannot tell. `fib.db.postgres`
takes the provider in its options map; `fib.http` (TLS, later) takes one the same way. A program that wants OpenSSL says so once, in `main`:

```clojure
(match (openssl/open-provider) ((Ok p) (run-app (dyn c/CryptoProvider :send p))) ((Err e) (die (. e message))))
```

There is **no** default provider and no `(c/default-provider)`: a program that does not pass one cannot compile a call that needs it, which is
the point (no surprise dependency on a C library in a program that never asked for one).

## 4. Memory safety at the C boundary (what a driver must do)

- Input bytes are lent to C by the address of the array's own data for the extent of the call; a key or password is never copied.
- A buffer C fills is allocated by the driver, copied out **once** into a fibber array, and, when it held secret material, cleansed
  (`OPENSSL_cleanse`, `memset_s`/`CC_`'s equivalents) before it is freed. Limits (documented in each driver): the fibber arrays that hold a
  password or key are ordinary arrays and are not zeroised when they are freed; the library's own context zeroises what it copied.
- A native context (an `EVP_MD_CTX`) is released **exactly once**: the hasher keeps its handle in an atom that goes to 0 on release, so a second
  `hasher-finish` or `hasher-close` is a `closed` error or a no-op, never a double free. fibber has no scope-exit hook yet (stdlib L12); until it
  does, a hasher that is abandoned without `hasher-finish` or `hasher-close` leaks its context until the process ends (not a crash). The one-shot
  functions in `fib.crypto.ops` close on every error path.
- `open-provider` runs a known-answer test, so a library that is broken, or an assumption about fibber's array layout that no longer holds,
  is an error at start-up, not a wrong digest later.

## 5. Encodings: the only code of ours

`fib.crypto.encoding` (hex, base64, base64url, padded and unpadded) is an encoding, not cryptography: it handles bytes, branches on public
data only, and is tested exhaustively (every length from 0 to 300, every byte value, the RFC 4648 vectors, and a random property). The
decoders are strict: a character outside the alphabet, missing or extra padding, a length that no input has and non-zero trailing bits are
`invalid-argument` errors (RFC 4648 section 3.5 allows refusing non-canonical input; a token that decodes two ways is worse than one that is
refused).

## 6. The contract

`fib.crypto.contract` is `CryptoContract`, a `fib.test` contract (docs/design/test-harness.md section 3). A driver repository runs it:

```clojure
(defspecs specs (implements CryptoContract "openssl" (fn () <a provider>)))
```

Fifteen scenarios, **published vectors only** (data in `fib.crypto.vectors`, generated once by `scripts/gen-crypto-vectors.sh`, which writes each
published value from its document and stops when python's hashlib/hmac or the `openssl` command disagree): FIPS 180-4 (SHA-256/384/512 of the
empty, `abc`, 448-bit, 896-bit and million-`a` messages), RFC 3174 and RFC 1321 (SHA-1, MD5, when offered), RFC 4231 test cases 1 to 7 for
HMAC-SHA-256/384/512 (keys shorter, equal to and longer than the block; one truncated), RFC 7914 section 11 and RFC 6070's inputs for
PBKDF2-HMAC-SHA256 including 4096, 80000 and 100000 iterations, RFC 5869 appendix A for HKDF-SHA-256; streaming in pieces of 1, 7, 64 and 65
bytes and a million bytes in pieces of 997; the hasher lifecycle (finish twice, feed after finish, close twice, a range outside the bytes);
argument refusals; random (length, not all equal, two draws differ, at least 200 distinct byte values in 4096, a negative count refused);
`ct=` correctness (not timing); and **capability honesty**: a listed name works, an unlisted one is an `unsupported` error, an unknown
algorithm is `unsupported`, and nothing outside the known names is listed.

**The contract can fail.** There is no fake crypto driver in fibber, so the proof lives in two places:
- fibber's gate (`specs/crypto-contract-shape-spec.fib`) runs the contract against a provider that supports *nothing* and one that
  *overclaims*: 13 of 15 scenarios fail for the first, exactly the legacy-digest and honesty scenarios hold (both are conditional on what a provider
  lists), and the honesty scenario fails for the second. It also checks the vector data is well formed (every hex string decodes, every length is
  the algorithm's).
- every driver repository runs the contract against `(Faulty real fault)` (`fib.crypto.fault`), a decorator that wraps the REAL provider and
  breaks one thing: `:truncate :flip-bit :wrong-alg :zero-random :ct-true :pbkdf2-plus :fallback :overclaim`, and expects the scenario about the
  broken thing to fail.

## 8. SCRAM-SHA-256 and the PostgreSQL driver

SCRAM (RFC 5802, RFC 7677) is: `SaltedPassword = PBKDF2(HMAC-SHA-256, password, salt, i)`, `ClientKey = HMAC(SaltedPassword, "Client Key")`,
`StoredKey = SHA-256(ClientKey)`, `ClientProof = ClientKey XOR HMAC(StoredKey, AuthMessage)`, `ServerSignature = HMAC(HMAC(SaltedPassword,
"Server Key"), AuthMessage)`, the nonce from `random-bytes`, base64 for the wire, `ct=` for the server signature. That is every provider
function it needs: `pbkdf2`, `hmac`, `digest`, `random-bytes`, `ct=`, and `base64` from the encodings. The messages and the state machine are
protocol logic and live in `fib.db.postgres`'s repository. `fib-crypto-openssl/specs/scram-spec.fib` computes the RFC 7677 exchange (user
`user`, password `pencil`) with provider calls only and reproduces the RFC's client proof and server signature byte for byte; it is a test helper,
not a published API.

## 9. AEAD, key agreement, signatures (built: CRYPTO-2)

The owner's rule holds and is the point of this section: **no primitive is ours**. The protocol below is what a native TLS 1.3 client needs and nothing more; a driver wraps a
library (OpenSSL's EVP today, CryptoKit and libsodium later); the contracts judge the driver against published vectors.

**Protocol** (`lib/fib/crypto/types.fib`). `CryptoProvider` gained five methods WITH DEFAULTS that answer `unsupported`, so a driver without them, and every earlier driver, still
compiles: `provider-aead-seal` and `provider-aead-open` (alg, key, nonce, aad, plaintext or sealed: `(Result (Array i8) CryptoError)`), `provider-generate-key` (alg) and
`provider-import-private` (alg, PKCS#8 DER) giving `(Result (dyn PrivateKey :send) CryptoError)`, and `provider-import-public` (SubjectPublicKeyInfo DER) giving
`(Result (dyn PublicKey :send) CryptoError)`. `Kdf` gained `KdfHkdfExpand (alg prk info length)` (under the `:hkdf` capability). Two handle protocols: `PrivateKey`
(`private-key-kind`, `private-key-public` raw, `private-key-agree` peer-raw, `private-key-sign` scheme msg, `private-key-close`) and `PublicKey` (`public-key-kind`,
`public-key-verify` scheme msg sig, `public-key-close`). A handle does its own operations, so it cannot be handed to another driver. Two new error kinds: `authentication-failed`
(an AEAD tag) and `invalid-signature`; a malformed key, point, signature or length is `invalid-argument`.

- **AEAD**: `:aes-128-gcm :aes-256-gcm :chacha20-poly1305`. Sealed = ciphertext || 16-byte tag. Nonce 12 bytes for all three (another length is `invalid-argument`: no
  variable-IV GCM, a TLS record never needs one). `aead-open` returns `authentication-failed` and no bytes for a bad tag, a short input, a changed AAD or nonce. The nonce is
  the caller's: reuse under one key is the caller's to avoid (TLS derives it from a counter), documented, not detectable here. Facts as functions: `aead-key-length`,
  `aead-nonce-length`, `aead-tag-length`. Not built (not cheap): an incremental or in-place variant. A record layer seals whole records; the OpenSSL driver writes the
  ciphertext into the result array directly (no copy) and decrypts into a buffer it cleanses.
- **Key agreement**: `:x25519 :ecdh-p256 :ecdh-p384` (P-384 is cheap and TLS 1.3 offers it; P-521 is not offered). A private key is a **handle**, never bytes: `generate-key`
  `:x25519 :p-256 :p-384`, the raw public encoding from `private-key-public` (X25519: 32 bytes; P-256, P-384: the uncompressed point, 65 and 97 bytes: a TLS key_share), the
  peer's key as raw bytes to `private-key-agree`. Raw private bytes enter only through `provider-import-private` as PKCS#8 (`fib.crypto.der/wrap-private` wraps a raw X25519 or
  Ed25519 key), for known-answer tests and stored keys; there is **no export**. A bad peer is an error, never a value: a wrong length, a point off the curve, a compressed point, and
  a **small-order** X25519 point (all-zero shared secret: RFC 7748 6.1, RFC 8446 7.4.2). The secret is fed to `hkdf`, never used raw.
- **Signatures, verify first**: schemes `:rsa-pss-sha256 :rsa-pss-sha384` (MGF1 with the same hash, salt length = hash length: TLS 1.3's rsae, so Wycheproof's valid signatures of
  salt length 0 or MGF1/SHA-1 are INVALID here), `:rsa-pkcs1-sha256 :rsa-pkcs1-sha384` (certificates still use it), `:ecdsa-p256-sha256 :ecdsa-p384-sha384` (DER signatures),
  `:ed25519`. Keys come from `import-public-key` over X.509 SubjectPublicKeyInfo DER (the whole array is one SPKI; an RSA key below 2048 bits and a type that does not verify are
  refused); a scheme that does not fit the key type is `invalid-argument`; only a valid signature is `Ok`. ECDSA's high-S form is accepted (valid in TLS; Wycheproof calls it
  acceptable) and no vector tests it either way. **Signing is a capability**: `:sign-ed25519 :sign-ecdsa-p256-sha256 :sign-ecdsa-p384-sha384`, by a `PrivateKey`; no RSA signing.
- **What TLS-1 needs and gets**: SPKI public-key import and verify (certificate chain, CertificateVerify), `generate-key` and `private-key-agree` (key share), `hmac` and
  `hkdf-extract` and `hkdf-expand` (HKDF-Expand-Label: the HkdfLabel bytes are TLS's own code), `aead-seal`/`aead-open` (records), `random-bytes`, `digest` (the transcript hash).
  What it must still do itself: **X.509 and ASN.1 parsing** (a certificate's SPKI, names, validity, extensions, the chain, path validation: protocol logic, written natively in
  TLS-1, not cryptography and not here), the HkdfLabel encoding, the record layer, the state machine, and a trust store.

**Vectors** (`vectors-aead`, `vectors-pk`, `vectors-tls`; `scripts/gen-crypto-vectors-pk.sh`): the sources are RFC texts and Project Wycheproof (a pinned commit), fetched by
`scripts/fetch-crypto-vectors.sh` into scratch against `specs/crypto-vectors.sha256`; the generator searches every RFC value in its RFC, recomputes each valid vector and refuses
each invalid one with python's `cryptography`, and writes a subset. Counts: AEAD 23 valid and 9 invalid (GCM specification test cases 2, 4 and 16, RFC 8439 2.8.2 and A.5,
Wycheproof); key agreement 25 valid (RFC 7748 5.2, 6.1, Wycheproof X25519, ECDH P-256 and P-384), 2 iterated (1 and 1000 rounds), 15 invalid (small-order points, off-curve
points, bad encodings); signatures 111 (32 valid, 79 invalid: Wycheproof RSA-PSS, RSA PKCS#1 v1.5, ECDSA, Ed25519 including malleability, bad DER and BER, truncated and extended
signatures, and the salt-length policy; RFC 8032 7.1); 2 Ed25519 signing known answers; 74 HKDF-Expand and 11 HKDF-Extract vectors (RFC 5869 appendix A, the whole key schedule of
RFC 8448, for TLS-1). The contracts derive MORE negatives from every valid vector at run time (one changed byte of ciphertext, tag, nonce, AAD, key, signature, message, peer key,
SPKI; truncations; extensions).

**Faults** (`fib.crypto.fault`, `pk-faults`): `:aead-skip-tag :aead-short-tag :aead-ignore-aad :aead-fixed-nonce :aead-flip-tag :accept-bad-point :kex-flip :public-flip
:accept-bad-sig :reject-good-sig :sign-flip`. A fault that changes a RIGHT answer needs a real library, so the driver's repository shows each one caught. Fibber's gate shows the
part that needs no library: against a provider that refuses everything (`Refuses`, in the shape spec, no cryptography) the negative scenarios HOLD and the positive ones fail, and
the faults that turn an error into a success (`:aead-skip-tag :accept-bad-point :accept-bad-sig`) make the negative scenarios fail; `fault-scenarios` ties each fault to a scenario
that exists.

TLS itself stays a library of its own (`fib.tls`), natively written (no libssl), over this interface.

### The Apple driver (design only, not built)

CommonCrypto is in libSystem (no extra link): `CC_SHA256_Init/Update/Final` (and `CC_SHA384`, `CC_SHA512`, `CC_SHA1`, `CC_MD5`), `CCHmacInit/Update/Final`
with `kCCHmacAlgSHA256` and friends, `CCKeyDerivationPBKDF(kCCPBKDF2, ..)` with `kCCPRFHmacAlgSHA256`, `CCRandomGenerateBytes`, and `timingsafe_bcmp` for
`ct=`. The contexts are plain structs a driver allocates. **HKDF, scrypt and Argon2id are not in the public CommonCrypto API** (HKDF is in CryptoKit,
a Swift API): writing HKDF over `CCHmac` ourselves is the cryptography the owner's rule forbids, so an Apple driver lists no `:hkdf`, and the contract,
which today requires `:hkdf`, would first have to make it optional like scrypt. That and `DYLD_INSERT_LIBRARIES` for the JIT are the open points. Not
built for want of budget, not for want of a machine: the Mac Studio (`ssh tmarsh@192.168.7.254`) answered.
