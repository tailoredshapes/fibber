# AVX-512: lane-generic kernels, the width table, and what a release binary can do

Status: implemented (kernels, table, `FIB_VECTOR_BITS`); runtime dispatch designed, not built.
Measurements: [docs/shootout/avx512-2026-10-06.md](../shootout/avx512-2026-10-06.md).
Related: ADR 0008 (v3 is the release baseline), [targets.md](targets.md), [simd-and-tensors.md](simd-and-tensors.md) 2.9.

## 1. What was true before

- `(native-lanes T)`, `f64xn` and `:native` come from the target's `vector-bits`: 256 for every AVX2 CPU in the table, including every AVX-512 one
  (`x86-64-v4`, `skylake-avx512`, `sapphirerapids`, `znver4`, ..): the design said "512 but preferred 256, as LLVM does".
- No kernel in `lib/fib/tensor` used `native-lanes`: every one hard-coded `f64x4` or `f32x8` (and the GEMM tiles were sized for AVX2's sixteen ymm
  registers). The shootout SIMD programs hard-coded `f64x4` (dot-product, saxpy, matmul, spectral-norm, n-body); `mandelbrot-simd` hard-coded `f64x8`.
- LLVM's behaviour, checked on the assembly (`FIB_TARGET_CPU=.. fibc emit | lair build --emit asm`, a program with an explicit `f64x8` loop and a scalar loop):
  - **An explicit 512-bit vector is honoured on every AVX-512 CPU**: `<8 x double>` code is zmm on `x86-64-v4`, `skylake-avx512`, `icelake-server`,
    `sapphirerapids` and `znver4`. `prefer-vector-width` is the auto-vectoriser's cost-model choice (`TuningPrefer256Bit`), not a legaliser limit;
    fibber's functions carry no `min-legal-vector-width`, so nothing splits an explicit 512-bit vector.
  - **Auto-vectorised scalar code**: the vectoriser takes 256 bits on `sapphirerapids`, `skylake-avx512`, `icelake-server` (`prefer-256-bit` is in their
    tuning) and 512 on `znver4`. Removing the feature (`(target (cpu "sapphirerapids") (features "-prefer-256-bit"))` in the lIR) gives zmm on SPR too.
    Measured in the report, section "prefer-vector-width".
- qemu-user 10.2's TCG has **no AVX-512** (`TCG doesn't support requested feature: avx512f`), so `qemu-x86_64 -cpu max` cannot run a zmm binary;
  a program built for `x86-64-v4` traps at start there, by its start-up CPU check. The 512-bit shape of the code is tested instead by running it at
  eight lanes on an AVX2 CPU (section 3); real zmm correctness is checked on AVX-512 hardware (the report).

## 2. The kernels: one source, a width parameter

- **GEMM** (`gemm-fma-f64`, `gemm-fma-f32`): every function takes a witness vector `w: (Simd f64 n)`; the tile follows the register file.
  - 256 bits (sixteen ymm): 6x8 f64 / 6x16 f32, twelve accumulators, two B vectors, one broadcast: 15 of 16 registers (unchanged).
  - 512 bits (thirty-two zmm): 6x32 f64 / 6x64 f32, **24 accumulators**, four B vectors, one broadcast: 29 of 32, no spill (the inner loop is 24
    `vfmadd231pd zmm` and four loads, checked in the object code). Of the shapes that fit, 6x4V has the fewest loads per fma, (6+4)/24 against
    (8+3)/24 for 8x24 and (12+2)/24 for 12x16; it keeps A's panel at six rows, so the packing is the same at every width. BLIS's skx dgemm uses a
    16x14 tile with 28 accumulators; this layout broadcasts A and vectorises along B's columns, so 24 is what 32 registers hold.
  - The inner block shrinks with the tile (a B panel, kc x NR elements, should stay in L1): 128 for the wide tile, 256 (f64) or 512 (f32) for the narrow.
    The report measures kc 64, 128 and 256 for the wide tile.
  - **Bit-identical across widths by construction**: each output is one fma chain over the inner index in increasing order, whatever its tile, block
    or width, so every width equals the checked scalar `fma-reference`. Cases 7960 (f64, 4 and 8 lanes) and 7961 (f32 with the fused bias and activation epilogue, 8 and 16
    lanes) compare the two shapes with each other and with the reference on 894 and 1015 shapes. `multiply-at a b (splat f64x8 0.0)` runs a width on any target.
- **Native-width kernels**: elementwise (`kernel-f64/32`), `exp`/`log`/`tanh` and the activations (`vmath`, one lane function over `(Simd f64 n)`), `sqrt`/`rsqrt`/`abs`/`sign`
  (`unary`), the axis reductions (`axis-lanes`), `sum-fast`/`dot-fast` (`simd-f64/32`) and the optimiser steps (`optim`) are written over `f64xn`/`f32xn` and
  `(native-lanes ..)`. Lane-wise kernels and the ordered axis folds are bit-identical at every width; `sum-fast`, `dot-fast` and the f64 `softmax`/`layernorm` row sums are
  reassociated by the lane count and differ in the last bits (the README never promised otherwise). Not widened: the mask kernels (`select`: `where`, `compare`, `relu-grad`
  build a lane mask from bytes with a vector literal of four or eight lanes) and the f32 `softmax`/`layernorm`, which work in eight-lane chunks at every width.
- **Language**: three small additions, none a new language feature for programs that do not use them. `load-simd p` / `store-simd p v` (a vector access through a raw pointer at the
  context's width, `load-f64x4` for every shape: spec/syntax.md); `(splat (Simd f64 n) x)` is accepted inside a function generic over `n` (the checker already inferred it,
  the lowering refused it); `FIB_VECTOR_BITS` overrides the native width for one run (`native.target/target-info`). New builtin names `load-simd`/`store-simd`
  are checked against the self-hosting trap (nothing in `compiler/` defines them). The compiler still builds with the released seed v0.1.7: only data and library
  code changed there.
- **Shootout SIMD programs**: `dot-product-simd`, `saxpy-simd`, `matmul-simd`, `spectral-norm-simd` are lane-generic (they print the scalar twin's md5 at 256 and 512 bits).
  `n-body-simd` is three-dimensional (x, y, z and a pad lane) and stays four lanes; `mandelbrot-simd` was already eight `f64` lanes (one zmm on AVX-512).

## 3. The width table

`compiler/types/targets.fib`, `cpu-rows-x86-512`: `x86-64-v4`, `sapphirerapids`, `graniterapids`, `znver4`, `znver5` prefer 512; `skylake-avx512` and its cousins (`skx`,
`cascadelake`, `cooperlake`, `cannonlake`, `icelake-*`, `tigerlake`, `rocketlake`) stay at 256: Skylake-X/Cascade Lake clock down under heavy 512-bit code, and the client cores have one
512-bit fma unit against two 256-bit ones (no gain from the wider vector). The host path (`FIB_TARGET_CPU` unset) uses the CPU name LLVM reports with the host's feature list:
`+avx512f` and a CPU whose row says 512 give 512. ADR 0008 is untouched: the release baseline is still `x86-64-v3`; the v4 rows are an optional extra.
`FIB_VECTOR_BITS=128|256|512` overrides the table for one run. A width the CPU lacks is legalised, so 512 on an AVX2 machine is correct at AVX2 speed: that is
how every kernel's 512-bit shape is tested here (`compiler/tests/lanes/lanes.sh`: the tensor cases at 512, checksums of the benchmark kernels at 256 and 512, the shootout md5s, the
zmm count of a v4 build; `scripts/mutant-avx512.sh`: 16 planted faults, each killed).

## 4. Runtime dispatch: what a v3 release binary can do

A binary built for `x86-64-v3` has no AVX-512 code. Three ways to give a numerics user 512-bit kernels:

(a) **Build for the host** (the default: `FIB_TARGET_CPU` unset). Works today: the compiler asks LLVM for the CPU, the table says 512, every kernel scales.
    The release tarball needs nothing: `fibc build` on the user's machine emits for that machine. This is the answer for anyone who compiles where they run.

(b) **Per-function targets plus a start-up dispatch**, for a binary built once and run on mixed machines. What it needs:
  1. lIR: a function modifier `(target (cpu "x86-64-v4") (features "+avx512f,..")?)` in `mod*` of `define` (spec/lir.md 4.5 is module-wide today). Lowering: `add-string-attribute`
     `"target-cpu"` and `"target-features"` on that function instead of the module's (the code is `native.lower/target-attributes`, which already takes a function and a target: the change is to
     look for the function's own first). The checker rejects a call from a function to a callee whose features are not a subset of the caller's *unless* it is the guarded dispatch below
     (LLVM refuses to inline a v4 callee into a v3 caller, which is what makes the call a real call).
  2. A way to say it in fibber: `(defun multiply-wide ... :target "x86-64-v4")` (an attribute on `defun`, carried to the emitter), and a primitive `(cpu-has? "avx512f")`, a bool read from a
     global that `fib.rt` fills once at start from the same cpuid/xgetbv code as `emit.cpucheck`.
  3. Instances: the lane count is chosen by the front end, per type, so the v4 copy is the generic instance at eight lanes (`multiply-at a b (splat f64x8 0.0)` already is one):
     `multiply` becomes `(if (cpu-has? "avx512f") (multiply-at-v4 a b) (multiply-at a b (splat f64x4 0.0)))`. Every helper that `multiply-at-v4` calls and LLVM does not inline
     needs the same attribute, so the attribute must propagate to callee instances of the wide instantiation (a rule in the emitter: an instance that mentions a 512-bit vector type
     in its signature or body gets the v4 target; the v3 callers reach it only through the guard).
  4. Cases: a v3 build on an AVX-512 machine takes the wide path, on an AVX2 one the narrow path, and both equal `fma-reference`.
  Size: the reader, AST and checker rows for the modifier, the lowering change, the attribute on `defun` and its propagation, the builtin and its runtime cell, a spec section and about a
  dozen cases: about 250 lines across `compiler/lir`, `compiler/native`, `compiler/emit` and `compiler/types`, plus the spec. Not small, and not needed until the numbers say so.
  An `ifunc`-style resolver (dlsym-time) is not needed: a once-written global bool and a predictable branch cost nothing against a matrix multiply.

(c) **A `-v4` tarball**: the tarball's stage 2 is the compiler; the code that runs on the user's machine is emitted when the user builds. A v4 compiler would not make users' programs
    wider (they build for their own host, option (a)); it would only make the compiler itself faster on AVX-512 machines. Of no value for this question.

The recommendation, with the measured gain, is in the report (section "Recommendation").
