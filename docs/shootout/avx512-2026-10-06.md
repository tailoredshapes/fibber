# AVX-512 on Sapphire Rapids and Zen 4 (2026-10-06)

fibber's numeric kernels were written for 256-bit vectors. This round made them follow the target's vector width (design: [docs/design/avx512.md](../design/avx512.md))
and measured what 512-bit code buys on two clean cloud machines: a c7i.4xlarge (Intel Sapphire Rapids) and a c7a.4xlarge (AMD Zen 4). Raw outputs, the build and run scripts
and the analysis scripts are in [`avx512-2026-10-06/`](avx512-2026-10-06/).

**Summary.**

- **Sapphire Rapids: 512 bits is a large win for compute-bound code.** Single-thread matmul goes from 45 to 47 GFLOPS (f64) and 94 to 97 (f32) at 256 bits to 76 to 82 and 156 to 167
  at 512 (1.6 to 1.75 times). The fused dense layer is 1.65 times faster and the autodiff training step 1.35 to 1.46 times (SGD 1.376 to 0.943 ms, Adam 1.534 to 1.139 ms).
  Before, fibber's matmul took 1.65 to 1.94 times NumPy+OpenBLAS's time on this machine; now it takes **1.02 to 1.15 times** (f64) and 1.01 to 1.12 (f32), the dense layer is 4 percent
  *faster* than NumPy (0.96) and the autodiff step is **7 percent (SGD) and 29 percent (Adam) faster than NumPy**.
- **Zen 4: a modest win, at parity with OpenBLAS.** Zen 4 runs a 512-bit operation as two 256-bit halves, so the matmul peak does not change: 49 to 50 GFLOPS (f64) at 256 bits, 55 at 512
  (1.10 to 1.14 times; f32 1.05 to 1.07). That is **0.96 to 0.99 of OpenBLAS's time (fibber is a little faster)**. `exp`, `log` and `tanh` are 1.3 to 1.5 times faster, softmax and layernorm
  1.3 times; the MLP and autodiff step do not change.
- Memory-bound kernels (elementwise `a*b+c`, the ordered sums, `max`, broadcast) do not change with the width: one thread's memory bandwidth is the limit (7.6 GB/s on this c7i, 23 GB/s on the c7a).
- Every program printed the same checksum at both widths, and the 68 case programs (34 cases, each built for 256 and 512 bits) print 0 on both machines: the zmm code is correct on real
  hardware. The one checksum that differs (`softmaxfused`, f64) is a reassociated sum, as documented.
- LLVM's `prefer-vector-width` matters little for fibber's auto-vectorised scalar code: 1.13 times on a compute-bound L1-resident loop on Sapphire Rapids, nothing on Zen 4 (which already
  vectorises at 512) or on the memory-bound shootout loops.
- The round cost about $0.7 of compute (two instances for 26 minutes), against the $6 cap.

## 2. What was built and how it was checked

Everything was compiled on lilnas (an i7-14700KF with no AVX-512), from commit 5192059 of branch `worktree-agent-aaea0e0e4c75e9c11` (stage 2 built by the released seed v0.1.7); the instances ran
binaries, NumPy and a shell script.

1. Stage 2 `F` (`fibc`) and `lairf` (`L`), then for each machine `build-all.sh MACHINE CPU` (`FIB_TARGET_CPU=sapphirerapids` or `znver4`, static, `gcc -static` at the link):
   `FIB_EMIT_EXE=1 FIB_TARGET_CPU=CPU FIB_VECTOR_BITS=256|512 F emit -I lib P.fib > P.lir`, `L build P.lir -o P.o -O 2 --emit obj`, `gcc -static`.
   `FIB_VECTOR_BITS` sets what `f64xn`, `:native` and `(native-lanes T)` stand for (the table gives 512 for both CPUs by default; the variable makes the 256 build possible for the same CPU).
   The scalar twins with LLVM's default width and with `-prefer-256-bit` differ in one line of the lIR: `(target (cpu "sapphirerapids") (features "-prefer-256-bit"))`.
   Programs: `scripts/bench/tensor/bench.fib` (the tensor table), `scripts/bench/autodiff/mlp.fib` (the MLP training step), the shootout SIMD programs and their scalar twins,
   `scripts/bench/lanes/poly.fib` (an auto-vectorised compute-bound loop) and 35 tensor cases built as programs.
2. Checks before launch: the full gate (`GATE_FRESH=1 FIBC=<seed> scripts/gate.sh --full`: PASS, 9 ADRs accepted); the tensor cases (101 of them) at `FIB_VECTOR_BITS=512` on the AVX2 host,
   where LLVM splits the eight-lane vectors (`compiler/tests/lanes/lanes.sh`); 16 planted faults, each killed (`scripts/mutant-avx512.sh`); the shootout md5s at both widths;
   a 256-bit `x86-64-v3` build of the whole bundle run end to end in smoke mode on this host. **qemu cannot run the 512-bit binaries**: qemu-user 10.2's TCG has no AVX-512
   (`TCG doesn't support requested feature: CPUID[eax=07h,ecx=00h].EBX.avx512f`, for `-cpu max` and `-cpu SapphireRapids`), and a program built for it traps at start (its CPU check). The zmm
   code was therefore first run on the instances, where the case programs came first.
3. On the instances `run-avx.sh` ran: the case programs (both widths; main's value is printed, 0 is a pass); the benchmark kernels' checksums at both widths on small sizes; the tensor table
   (`scripts/bench/tensor/run.py --fibc true --bin BIN --openblas DIR`, median of 5 timed runs after one warm-up, NumPy on OpenBLAS in the same process layout); the shootout programs
   (median of 5 wall times, md5 checked against the scalar twin's); and the autodiff step (200 steps, 5 runs, median of the median step). Every timed program is one thread pinned with
   `taskset -c 4`; OMP/OpenBLAS threads are 1. One job at a time.
4. A first pass of the same script (before the inner block of the wide tile was changed from 128 to 512, section 5) is the source of the inner-block sweep; the tables below are the second pass
   with the final code. The 256-bit builds did not change between the passes, so they also measure the run-to-run noise: matmul f64 2048 at 256 bits took 382.3 and 378.4 ms (SPR), 353.1 and 353.3 ms (Zen 4).

**What limits each kernel.**

- *matmul, dense layer, MLP, autodiff step*: arithmetic. At 512 bits on Sapphire Rapids fibber reaches 76 to 82 GFLOPS (f64), about 75 to 80 percent of the estimated peak, OpenBLAS 78 to 88;
  the gap to OpenBLAS grows with the size (1.02 at n = 512, 1.15 at 2048), which suggests the cache blocking: the packed B block (512 x 1024 f64 = 4 MB) does not fit the 2 MB L2. Not tuned further.
  At 256 bits fibber reaches 92 percent of that width's peak, so the whole gain is the wider FMA. On Zen 4 both widths sit at the 256-bit pipe limit (about 50 to 55 of 56); the extra 10 percent at 512 is
  fewer instructions and loads, and fibber then matches OpenBLAS's AVX-512 kernels.
- *exp, log, tanh, softmax, layernorm*: polynomial arithmetic plus memory. Zen 4 (23 GB/s per thread) shows 1.3 to 1.5 times; on Sapphire Rapids one thread's 7 GB/s bandwidth caps them
  (80 MB in and out in 25 ms): 1.1 to 1.2 times.
- *elementwise, ordered reductions, broadcast*: DRAM bandwidth (arrays of 800 MB); no change. `sum axis 0` and `max axis 0` (adding whole rows) gain 1.6 and 1.9 times on Sapphire Rapids (they stream
  rows from L3/DRAM with two loads per add) and little on Zen 4.
- *Rows that do not use the native vectors* (ordered sum, mean, max, axis 1, broadcast) differ by up to 17 percent between the two builds, in both directions (`max` 0.88 and 0.87 on Sapphire Rapids,
  `sum` 1.17 on Zen 4). The source and the CPU are the same, so this is code layout, not the width; treat 15 percent as the noise floor of those rows. Not investigated.
- *dot-cache, matmul-simd, saxpy/dot at memory size*: `dot-cache` (32768 elements, L2-resident) gains 1.19 times on Sapphire Rapids; `matmul-simd` (a four-accumulator row kernel) 1.32 and 1.49 times;
  the memory-size loops are bound by bandwidth. `spectral-norm` is bound by the division.

The 6x32 (f64) and 6x64 (f32) tile first used an inner block of 128 (a B panel kc x NR stays in L1). A sweep on both machines (GFLOPS, single thread; `avx512-2026-10-06/*/kc-sweep/`) showed larger is better:

## 6. `prefer-vector-width` and auto-vectorised scalar code

LLVM's vectoriser takes 256 bits on `sapphirerapids`, `skylake-avx512` and `icelake-server` (the `prefer-256-bit` tuning) and 512 on `znver4`; explicit 512-bit vectors are honoured on all of them (the
assembly of `<8 x double>` code is zmm on every AVX-512 CPU, checked with `prefer-vector-width.sh`; fibber's functions have no `min-legal-vector-width`). A compute-bound, L1-resident loop that
LLVM vectorises (`scripts/bench/lanes/poly.fib`: a degree-5 polynomial over 1024 doubles, 2 x 10^6 times), median of 5 wall times:

| machine | default width | -prefer-256-bit | |
|---|---|---|---|
| Sapphire Rapids | 0.60 s | 0.53 s | 1.13x |
| Zen 4 | 0.46 s | 0.46 s | 1.00x |

The shootout's scalar twins (table above: saxpy, dot-product, matmul, spectral-norm) show 1.00 times, 1.05 at best (saxpy-cache): they are memory-bound, divide-bound, or not vectorised.
So `prefer-vector-width` matters by 13 percent on one kind of loop on Sapphire Rapids and nothing elsewhere here; it is not worth a table row or a flag. Code that wants 512 bits writes
`f64xn` (or an explicit eight-lane vector).

## 7. Recommendation: runtime dispatch

**Do (a), already done; do not build (b) yet.** (a) is that a program built for the host (the default, `FIB_TARGET_CPU` unset) gets 512-bit kernels on Sapphire Rapids and Zen 4: nothing to ship but the kernels
and the table rows. The gain it buys is large only on Intel server cores (1.65 times the matmul and dense layer, 1.35 to 1.46 times the autodiff step; fibber then beats NumPy on OpenBLAS on those
workloads) and small on Zen 4 (1.1 times; 1.3 to 1.5 on exp/log/tanh). (b), per-function targets with a start-up dispatch (docs/design/avx512.md, section 4: about 250 lines in `compiler/lir`, `native`,
`emit` and `types` plus the spec and cases), only matters for a binary built once and run on both AVX2 and AVX-512 machines, which a numerics user who compiles where they run does not have; a user who ships
a binary can build one for `x86-64-v3` and one for `x86-64-v4` (a v4 build traps at start with a clear message on a CPU without AVX-512). If prebuilt numerics binaries become a use case, (b) is
justified by the Sapphire Rapids numbers (1.65 times on the kernels that dominate training) and is the next step; Zen 4 alone would not justify it. (c), a `-v4` tarball, buys nothing: the release
tarball is the compiler, and programs are compiled on the user's machine.

The table rows: `x86-64-v4`, `sapphirerapids`, `graniterapids`, `znver4`, `znver5` prefer 512. Measured: Sapphire Rapids and Zen 4. **Not measured, set by reasoning:** Granite Rapids
(same core family as Sapphire Rapids), Zen 5 (a full-width 512-bit datapath, so at least Zen 4's gain), and the rows that stay at 256 (`skylake-avx512`, `cascadelake`, `icelake-*`, `tigerlake`, `rocketlake`: heavy 512-bit code lowers the clock
on Skylake-X and Cascade Lake, and the client cores have one 512-bit FMA unit). ADR 0008 is unchanged: v3 stays the release baseline; the v4 rows are an extra.

## 9. Caveats

- One instance of each type, one day, five runs each: single-run-day noise (neighbours, clocks) is possible; the 256-bit builds measured twice agree within 1 to 2 percent on the compute-bound rows.
- Clocks and AVX-512 frequency licences were not measured; the peak figures are estimates.
- Single thread only. The multi-thread behaviour of a 512-bit kernel (Sapphire Rapids lowers its clock with more cores in heavy AVX-512 use) was not measured.
- The rows for Granite Rapids and Zen 5 are by reasoning, and Skylake-X and client AVX-512 cores were not available.
- NumPy 1.26.4 with Ubuntu's OpenBLAS 0.3.26; a pip wheel with a newer OpenBLAS was not measured.
- The benchmark inputs are dyadic, so the checksum comparison does not show reassociation in sums; the bit-level comparison is in the cases.
