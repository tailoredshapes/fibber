# One benchmark round on AWS: Sapphire Rapids and Graviton4 (2026-10-06)

One round of the shootout, the tensor table, the `fib.parallel` scaling rows and the autodiff training step on two dedicated cloud
machines, both otherwise idle, so the numbers do not carry the noise of the shared development machine (lilnas). Raw outputs, the build
script and the driver are in [`aws-2026-10-06/`](aws-2026-10-06/).

**Summary.** Every output matched its md5 or checksum, on both machines (53 of 53 shootout rows each, 26 of 26 tensor rows each, every
`fib.parallel` checksum the same at every worker count).

- The shootout picture is the same as on lilnas. fibber is at C's speed on fannkuch-redux, fasta and mandelbrot (scalar), and well
  ahead of C with the SIMD programs on mandelbrot. It is ahead of C on binary-trees on Graviton4. The large gaps remain:
  - k-nucleotide: 16x C on x86 and 22x on ARM.
  - pidigits: 8x C.
  - scalar n-body: 3.8x C.
- The SIMD builds bring n-body to C (1.12x on x86, 0.95x on ARM).
- Single-thread tensor kernels: fibber's matmul is 1.3 to 1.9 times slower than NumPy on OpenBLAS on Sapphire Rapids. On Graviton4 it
  is 4 to 12% *faster* than NumPy with Ubuntu's OpenBLAS.
- `preduce` and the fixed tree scale with cores: up to 31x on the 32 Graviton4 cores. `pmap` and `pmap-each` do not scale: 1.2x to 1.4x
  at any worker count, on both machines.
- The autodiff step is 1.4 to 1.5 times NumPy's on x86. On Graviton4 it is 0.92 (SGD, faster than NumPy) and 1.05 (Adam).

The whole round cost about $1.59, against an $8 budget.

## 2. What was built, and how

Everything was compiled on lilnas, from main at 6b9ca18 (`plant-vec.sh: run over the Vec spec files only`). The instances only ran
binaries, plus gcc and javac for the C and Java twins.

1. Stage 2: `FIB_LIB=<tree>/lib fibc-0.1.7 build compiler/fibc.fib -I compiler -I lib -L /usr/lib/llvm-21/lib -l LLVM-21 -o F`
   (149 s). Then `lairf` from it: `F build compiler/lairf.fib -I compiler -I lib -L /usr/lib/llvm-21/lib -l LLVM-21 -o L`.
2. Each benchmark program went through `aws-2026-10-06/build.sh`. All binaries are static, which is what lets them run on 24.04's
   older glibc.
   - x86: `FIB_EMIT_EXE=1 FIB_TARGET_CPU=sapphirerapids F emit -I lib P.fib > P.lir`, then `L build P.lir -o P.o -O 2 --emit obj`,
     then `gcc -static P.o -o P -lm -lpthread`.
   - ARM: `FIB_EMIT_EXE=1 F emit --target aarch64-unknown-linux-gnu -I lib P.fib`, with the module's first line set to
     `(target (cpu "neoverse-v2"))`. Then `FIB_TARGET_CPU=neoverse-v2 L build P.lir --target aarch64-unknown-linux-gnu -o P.o -O 2
     --emit obj`, then `aarch64-linux-gnu-gcc -static P.o -o P -lm -lpthread`, linked on lilnas.
   - Programs: the scalar and `-simd` program of every shootout directory, `scripts/bench/tensor/bench.fib`,
     `scripts/bench/autodiff/mlp.fib`, and `scripts/bench/parallel-closure.fib`. Also
     `docs/shootout/parallel/preduce-1e8.fib`, with its 28-worker columns changed to 32.
3. Checks before launch:
   - The same pipeline at `FIB_TARGET_CPU=x86-64-v3` passed every small shootout size on lilnas: 23 of 23 md5. lilnas is a Raptor
     Lake with no AVX-512, so the `sapphirerapids` binaries crash there and were first checked on the instance.
   - The ARM binaries passed the same 23 under `qemu-aarch64 -cpu max`.
   - The tensor, autodiff and parallel binaries agreed with NumPy and with each other at small sizes, both natively and under qemu.
4. On the instances, `aws-2026-10-06/run-all.sh` ran the round:
   - It built the C twins (`gcc -O3 -march=native|-mcpu=native`, plus `-ffp-contract=off` and `cflags` as `scripts/shootout/run.sh`
     adds them) and the Java twins (`javac`).
   - It generated the fasta inputs with the Java fasta twin. Their md5 matched sizes.txt: 25 000 000 is fd55b9e8…, 5 000 000 is
     29b8ecce….
   - Then it timed everything in turn, one job at a time, on an otherwise idle machine.
   - The tensor rows used `scripts/bench/tensor/run.py --fibc true --bin bin/tensor-bench --openblas DIR`, the repository's driver
     with the build step skipped.

**Two findings from the build** (not fixed here):

1. `F emit --target aarch64-unknown-linux-gnu` with `FIB_TARGET_CPU=neoverse-v2` set aborts with `LLVM ERROR: 64-bit code requested
   on a subtarget that doesn't support it!` for any program whose macros the expander runs through the host JIT. The JIT is given
   the AArch64 CPU name on x86. The workaround above is to emit without `FIB_TARGET_CPU` and give the CPU to `lairf` only.
2. `F emit` without `FIB_EMIT_EXE=1` emits the case-kind module, which prints `main`'s value at exit. This adds a trailing `0` line
   to every output, so every md5 failed until the variable was set.

How to read the table:

- **Against OpenBLAS on Sapphire Rapids,** fibber's matmul is 1.3 to 1.9 times slower. On lilnas it was 1.4 to 2.1 times slower
  (`docs/shootout/tensor.md`). OpenBLAS on SPR has AVX-512 kernels. fibber was built for `sapphirerapids`, but the library's
  kernels are written for 256-bit lanes.
- **On Graviton4, fibber's matmul beats Ubuntu's OpenBLAS** by 4 to 12%. Ubuntu noble's OpenBLAS may not have tuned Neoverse-V2

  are 5 to 10 times NumPy. On SPR they are 2 to 3 times. `t/sum-fast` beats NumPy on both, so the cost is the ordered (scalar,
  dependency-chained) contract and the closure-style `max`, not memory bandwidth.

| | sequential | tree W=1 | 2 | 4 | 8 | 16 | 32 | `preduce-n` W=8 | `preduce-range` W=32 |

The fixed tree's sum was -7.142857140969321 at every worker count on both machines, the same bits as on lilnas.

- **Reductions scale.** On Graviton4's 32 real cores, `preduce-n`, `preduce-range` and the fixed tree scale almost linearly to 32
  workers (29x to 31x). On SPR they flatten after 16 workers, the physical core count.
- **`pmap` and `pmap-each` do not scale on either machine.** At 1e8 elements they are 1.2x to 1.4x faster with 32 workers than with
  one. A time that hardly moves with W points to serial work that dominates. Likely candidates are building the result `Vec` of 1e8
  elements, or the allocation it needs, but neither was profiled.
  - lilnas measured `pmap-each` at 1e7 elements: 344 ms at 1 worker and 37 ms at 16 (`docs/shootout/parallel.md`), so this
    workload is different.
  - This is the one finding of the round worth following up.
